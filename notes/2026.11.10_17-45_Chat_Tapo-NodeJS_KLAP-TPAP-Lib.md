## 1. Fehler mit `tp-link-tapo-connect`

**Ich:**
TAPO nodejs: benutze lib `tp-link-tapo-connect@latest`

```
connect to device: Lichterkette (F0-09-0D-BD-3C-F7)...
Failed to login due to Error: handshake1 failed: Error: Request failed with status code 403
Falling back to legacy login method
.../tapo-utils.js:96
            case 1003: throw new Error("Device supports KLAP protocol - Legacy login not supported");
Error: Device supports KLAP protocol - Legacy login not supported
    at checkError (.../tapo-utils.js:96:30)
    ...
Node.js v20.19.2
```

**Copilot:**
Die eigentliche Ursache ist der **403 beim KLAP-Handshake1**. Das Gerät spricht also KLAP, lehnt aber die Anmeldung ab. „Legacy login not supported“ ist nur eine Folge davon, denn die Lib versucht danach automatisch das alte Protokoll.

Prüfen (in dieser Reihenfolge):
1. **Third-Party Compatibility** in der Tapo-App (Ich → Drittanbieterdienste) aus- und wieder einschalten, auch wenn sie schon an ist. Am besten im selben WLAN wie das Gerät.
2. Gerät danach ca. 15 s vom Strom nehmen.
3. Zugangsdaten = **TP-Link/Tapo-Konto** (E-Mail + Passwort), nicht WLAN-Passwort. Groß-/Kleinschreibung beachten.
4. Firmware prüfen: Bei Firmware 1.4.x funktioniert die lokale API teils nicht mehr. Bei P100 mit neuer Firmware wurde ein neues Verfahren **„TPAP“** beobachtet.

Test, ob es an den Zugangsdaten liegt:

```js
const { cloudLogin, loginDeviceByIp } = require('tp-link-tapo-connect');

(async () => {
  const email = 'deine@mail.de', pw = 'deinPasswort', ip = '192.168.x.x';
  const cloud = await cloudLogin(email, pw);
  console.log('Cloud OK:', (await cloud.listDevices()).map(d => d.alias));
  const dev = await loginDeviceByIp(email, pw, ip);
  console.log(await dev.getDeviceInfo());
})().catch(e => console.error('Fehler:', e.message));
```

- Cloud OK, lokal 403 → Third-Party-Freigabe oder Firmware/Protokoll.
- Cloud schlägt fehl → E-Mail/Passwort falsch.

## 2. Kann die Lib das Protokoll?

**Ich:**
Cloud login hat geklappt, musste die Kompatibilitätseinstellung vorher nicht aktivieren, hat sonst immer ohne geklappt. Prüfe ob die lib das Protokoll kann.

**Copilot:**
Nein, `tp-link-tapo-connect` kann das neue Protokoll nicht. Es kennt nur Legacy-AES, KLAP und Cloud-Passthrough. Die Lichterkette hat sehr wahrscheinlich per Firmware-Update auf **TPAP** umgestellt und spricht KLAP nur noch mit eingeschalteter Third-Party Compatibility.

- Ab Firmware 1.4.0 (Steckdosen) bzw. 1.4.1–1.4.3 (Lampen) nur noch mit eingeschaltetem Modus.
- TPAP nutzt **SPAKE2+** (RFC 9383) statt Hash-Abgleich → KLAP-Versuch gibt 403 → Fallback auf Legacy → beide Fehlermeldungen.
- Lib: letztes Release 2.0.15, kein TPAP.

| Option | Aufwand | Hinweis |
|---|---|---|
| 1. Third-Party Compatibility einschalten | minimal | Gerät spricht wieder KLAP, Code läuft unverändert |
| 2. Python/Rust-Lib `tapo` ab v0.11.1 | mittel | kann TPAP, erkennt Protokoll automatisch |
| 3. Referenz-Client `tapo-tpap-client` (Python) | mittel | TPAP vollständig, getestet mit L920/L930 |

Wichtig: **keine Login-Retry-Schleife**, zu viele Fehlversuche sperren das Gerät (`TPAP_AUTH_ATTEMPTS_LIMIT`).

## 3. Eigener KLAP-Client

**Ich:**
ok habe ich aktiviert, kannst du mir trotzdem diese lib (bzw.) einen eigenen minimalen Handshake-Weg selber coden?

**Copilot:**
Eigener KLAP-Client `tapo-klap.js`: ~90 Zeilen, ohne npm-Pakete. Gegen ein simuliertes Gerät getestet (an/aus/info, falsches Passwort wird erkannt).

```bash
TAPO_USER='deine@mail.de' TAPO_PASS='pw' node tapo-klap.js 192.168.x.x on
TAPO_USER='deine@mail.de' TAPO_PASS='pw' node tapo-klap.js 192.168.x.x off
TAPO_USER='deine@mail.de' TAPO_PASS='pw' node tapo-klap.js 192.168.x.x
```

Ablauf:
1. **handshake1:** 16 Zufallsbytes → Gerät antwortet mit eigenen 16 Bytes + Prüf-Hash. Auth-Hash: `sha256(sha1(mail) + sha1(pw))`.
2. **handshake2:** Gegenbeweis an das Gerät.
3. **Sitzung:** Schlüssel/IV/Signatur ableiten (`lsk`, `iv`, `ldk`), dann AES-128-CBC + SHA256-Signatur + Sequenznummer an `/app/request?seq=`.

## 4. HTTP 400 bei handshake1

**Ich:**
```
node tapo-klap.js 192.168.178.23 info
Fehler: /handshake1: HTTP 400
```

**Copilot:**
400 = Anfrage wird formal abgelehnt, noch vor der Passwortprüfung. Vermutung: `fetch` schickt zusätzliche Header (`sec-fetch-mode`, `accept-language`), die der Tapo-Webserver nicht verarbeitet. → Umgestellt auf Nodes `http`-Modul mit minimalen Headern, plus `TAPO_DEBUG=1`.

```bash
TAPO_DEBUG=1 TAPO_USER='deine@mail.de' TAPO_PASS='pw' node tapo-klap.js 192.168.178.23 info

# direkter Test
head -c16 /dev/urandom | curl -s -i -X POST --data-binary @- \
  -H 'Content-Type: application/octet-stream' http://192.168.178.23/app/handshake1 | head -5
```

## 5. KLAP läuft – aber nicht ohne Third-Party-Modus

**Ich:**
```
TAPO_DEBUG=1 node tapo-klap.js 192.168.178.23 info
Lichterkette | P100 | FW 1.4.6 Build 260617 Rel.064743 | an: true
```
Klappt erstmal einwandfrei. Wenn ich jetzt aber den Drittanbieter-Modus ausmache:
```
DEBUG /handshake1 403 { server: 'SHIP 2.0', 'content-length': '0', 'content-type': 'text/html' }
Fehler: /handshake1: HTTP 403
```
Können wir das so bauen, dass es ohne Drittanbieter-Modus geht?

**Copilot:**
Ja, aber nicht als kleine Änderung am KLAP-Handshake. Die „Lichterkette“ ist eine **P100 mit FW 1.4.6**, die ohne den Modus nur **TPAP** spricht: SPAKE2+ über P-256, danach AES-CCM/GCM oder ChaCha20, Schlüssel per HKDF.
Den Referenzcode (`tpap_proto.py`) konnte ich nur bruchstückhaft lesen. Ohne die genaue Ableitung von `w0`/`w1`, das Nachrichtenformat und den Bestätigungsschritt will ich nicht raten (Fehlversuche → Sperre).

- **Weg A (empfohlen):** `tpap_proto.py` schicken → 1:1-Port nach Node, ohne Pakete, Kurvenarithmetik mit `BigInt`.
- **Weg B:** Python-Lib `tapo` (ab 0.11.1) per `child_process` aufrufen.

## 8. Feinschliff der API-Idee

**Ich:**
- Energie P110 gut; `get_device_usage` klappt bei mir schon
- Timer und „alles wie App“ erstmal raus
- Session renew und `.on`-Events gut
- watch-Intervall in ms, einfach halten
- watch als Array statt Objekt? Name/Infos optional watchbar
- Idee: `pc.watch(5e3,"state","info"); pc.watch(1e3,"currentPower"); pc.watch(10e3,"energyMonitor");`
- beide Protokolle rein, Netzwerk-Scan unnötig
- Können P100 Zeitpläne?
- `unwatch` mit Parametern
- Sauber: `get_device_usage` haben P100+P110, Energie nur P110 → so auch in der API. Funktionen camelCase (`getSomething()`)
- Triggert `reauth`/`offline` ohne Watch erst beim nächsten eigenen Aufruf?
- `getCurrentPower()` soll Promise zurückgeben und zusätzlich das `.on`-Event auslösen

**Copilot:**
Gebaut als `tapo.js` (KLAP + TPAP, Auto-Erkennung, Watch/Unwatch, Events, Session-Erneuerung) + `beispiel.js`. Nur gegen simulierte Geräte getestet.

- Intervall in **ms**, kein Minimum; hängt ein Abruf, wird der nächste übersprungen.
- `watch(5e3, 'state', 'info')`: ein Timer pro Thema, erneutes `watch` ersetzt nur dieses Intervall.
- Themen = Getter ohne `get`: `state`, `info`, `deviceUsage`; P110 zusätzlich `currentPower`, `energyUsage`.
- `tapo.connect(ip)` liefert `P100` oder `P110`; nur `P110` hat Energie-Methoden; falsches Thema → `TypeError`.
- camelCase überall, Rückgaben auch (`deviceOn`), `nickname` dekodiert.
- Jeder Getter: Promise **und** Event `(wert, alt)`, `change` nur bei Änderung.
- `unwatch('energyUsage')`, `unwatch()`, `tapo.unwatchAll()`, `pc.watching`.

**reauth/offline/online:** Ohne Watch kommen sie erst beim nächsten eigenen Aufruf, mit Watch beim nächsten Durchlauf.
- Offline → nur `discover` ohne Login, dann einmal Login → `online`
- Session abgelaufen → 1× Re-Login → `reauth`
- Falsches Passwort → Watches pausieren (`authBlocked`), eigener Aufruf versucht es wieder

Testergebnisse (simuliert, P110/TPAP + P100/KLAP): Erkennung, an/aus/toggle, watch/unwatch, reauth, offline/online, falsches Passwort ✅.
Offen: echte P110-Feldnamen/Einheiten; Verhalten bei abgelaufener TPAP-Session (Lib behandelt jeden HTTP-/Entschlüsselungsfehler als Session-Fehler).

**Zeitpläne P100:** ja, laufen auf dem Gerät. Testen mit `kette.request('get_schedule_rules')`.

## Kurzreferenz API (`tapo.js`)

```js
const { Tapo, TapoError } = require('tapo-lan');
const tapo = new Tapo({ user, pass });

const kette = await tapo.connect('192.168.178.23');            // P100
const pc    = await tapo.connect('192.168.178.30', { name: 'PC', protocol: 'auto', port: 80 }); // P110

// alle Geräte
await kette.getInfo(); await kette.getState(); await kette.getDeviceUsage();
await kette.setState(true); await kette.turnOn(); await kette.turnOff(); await kette.toggle();
await kette.request('get_schedule_rules');                    // roh, snake_case

// nur P110
await pc.getCurrentPower(); await pc.getEnergyUsage();

// Watch
pc.watch(1e3, 'currentPower'); pc.watch(10e3, 'energyUsage'); kette.watch(5e3, 'state', 'info');
pc.unwatch('currentPower'); pc.unwatch(); tapo.unwatchAll();
pc.watching; pc.topics; pc.last; pc.online; pc.authBlocked;

// Events (Gerät: (wert, alt) | Hub: (gerät, wert, alt))
// state, info, deviceUsage, currentPower, energyUsage, change, online, offline, reauth, error
```

Debug: `TAPO_DEBUG=1`
